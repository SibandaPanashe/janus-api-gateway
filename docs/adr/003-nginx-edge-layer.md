# ADR-003: Nginx Handles First-Line Rate Limiting, Not Spring Boot

## Status
Proposed

## Context
Janus needs to protect the Spring Boot core engine from two categories
of abusive traffic:

1. **Volume attacks** — a single IP sending thousands of requests per
   second, exhausting thread pools before application logic even runs
2. **Slow connection attacks** — clients that open connections and send
   data slowly, holding threads open indefinitely

The question is: at which layer does the first line of defence live?

Two options were evaluated:
1. Handle all traffic in Spring Boot with a filter/interceptor
2. Put Nginx in front of Spring Boot as a reverse proxy and edge layer

## Decision
Deploy Nginx as a reverse proxy in front of the Spring Boot engine.
Nginx handles three specific concerns before a request reaches Java:

**Layer 1 — Connection limiting (`limit_conn_zone`)**
Caps the number of concurrent open connections per IP address.
Slow connection attacks are killed here before they consume threads.

**Layer 2 — Request rate limiting (`limit_req_zone`)**
Enforces a static burst rate per IP using a leaky bucket algorithm.
This handles volumetric abuse — bots, scrapers, misconfigured clients —
without the request touching the JVM.

**Layer 3 — Micro-caching (`proxy_cache`)**
Public, unauthenticated GET endpoints (e.g. pricing tiers, API
documentation) are cached at the Nginx layer for 5 seconds.
A cached response served by Nginx costs microseconds.
The same response generated by Spring Boot costs milliseconds and
consumes a thread. Under traffic spikes, this difference is significant.

## Why Not Handle Everything in Spring Boot?
Spring Boot runs on a thread pool. Every request — including abusive
ones — consumes a thread while it is being processed. If the thread
pool is exhausted, legitimate requests queue or fail.

Nginx is event-driven and non-blocking. It can hold thousands of
connections with minimal resource consumption and reject bad ones
before they reach the thread pool. This is the principle of
**load shedding at the earliest possible layer** — reject work cheaply
at the edge rather than expensively in the core.

A request rejected by Nginx costs ~50 microseconds.
A request that reaches Spring Boot and is then rejected costs
~5 milliseconds and holds a thread for that duration.
At scale, this is the difference between a system that degrades
gracefully and one that falls over.

## Consequences
- Volumetric abuse is stopped before it reaches the JVM ✅
- Thread pool is protected from connection exhaustion ✅
- Public endpoint responses served from cache reduce backend load ✅
- Nginx adds an operational component to deploy and monitor ⚠️
- Two rate limiting layers (Nginx static + Drools dynamic) must be
  kept logically consistent — Nginx limits should be looser than
  Drools limits to avoid Nginx blocking legitimate clients ⚠️
- TLS termination at Nginx means the internal Nginx→Spring
  connection is plain HTTP — acceptable on localhost/private
  network, must be reviewed for multi-host deployments ⚠️
