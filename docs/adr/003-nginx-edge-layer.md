# ADR-003: Nginx Handles First-Line Rate Limiting, Not Spring Boot

## Status
**Accepted** (Implemented May 2026)

## Context
Janus needs to protect the Spring Boot core engine from two categories
of abusive traffic:

1. **Volume attacks** — a single IP sending thousands of requests per
   second, exhausting thread pools before application logic even runs
2. **Slow connection attacks** — clients that open connections and send
   data slowly, holding threads open indefinitely

The question is: at which layer does the first line of defence live?

Two options were evaluated:
1. Handle all traffic in Spring Boot with a filter/interceptor
2. Put Nginx in front of Spring Boot as a reverse proxy and edge layer

## Decision
Deploy Nginx as a reverse proxy in front of the Spring Boot engine.
Nginx handles three specific concerns before a request reaches Java:

**Layer 1 — Connection limiting (`limit_conn_zone`)**
Caps the number of concurrent open connections per IP address at 20.
Slow connection attacks are killed here before they consume threads.

**Layer 2 — Request rate limiting (`limit_req_zone`)**
Enforces a static burst rate per IP using a leaky bucket algorithm:
30 req/s with burst=30, plus a secondary 10 req/s zone with burst=50.
This handles volumetric abuse — bots, scrapers, misconfigured clients —
without the request touching the JVM.

**Layer 3 — Micro-caching (`proxy_cache`)**
Public, unauthenticated GET endpoints (e.g. `/api/v1/public/*`) are
cached at the Nginx layer for 5 seconds. A cached response served by
Nginx costs microseconds. The same response generated by Spring Boot
costs milliseconds and consumes a thread.

## Implementation Detail

**Deployment:** Nginx 1.25-alpine in Docker, configured via
`nginx/nginx.conf` and `nginx/conf.d/janus-gateway.conf`.

**Custom Error Responses:** Nginx returns structured JSON for
rate-limited (429) and backend-down (503) responses, matching the
Janus API error format.

**Load Shedding:** `proxy_connect_timeout 3s`, `proxy_read_timeout 10s`,
`proxy_next_upstream_tries 2`. When the Java backend is degraded,
Nginx fails fast rather than queuing indefinitely.

**TLS Termination:** Nginx handles TLS 1.3 with self-signed certificates
for development. Internal Nginx→Spring Boot communication is plain
HTTP on localhost.

**WebSocket Passthrough:** `/ws/` location configured with
`proxy_http_version 1.1` and `Upgrade` headers for future dashboard
WebSocket support.

## Verified Performance

Benchmark: 100 rapid requests through Nginx edge.
- **200 responses:** 9 (requests that reached Java)
- **429 responses (Nginx):** 91 (blocked at edge before reaching Java)
- **Result:** Nginx absorbed 91% of abusive traffic without touching
  the JVM thread pool.

## Why Not Handle Everything in Spring Boot?
Spring Boot runs on a thread pool. Every request — including abusive
ones — consumes a thread while it is being processed. If the thread
pool is exhausted, legitimate requests queue or fail.

Nginx is event-driven and non-blocking. It can hold thousands of
connections with minimal resource consumption and reject bad ones
before they reach the thread pool. This is the principle of
**load shedding at the earliest possible layer** — reject work cheaply
at the edge rather than expensively in the core.

A request rejected by Nginx costs ~50 microseconds.
A request that reaches Spring Boot and is then rejected costs
~5 milliseconds and holds a thread for that duration.

## Consequences

| Outcome | Detail |
|---------|--------|
| ✅ Volumetric abuse stopped before JVM | Confirmed: 91% block rate at Nginx edge. |
| ✅ Thread pool protected | Java thread pool only sees 9% of abusive traffic. |
| ✅ Custom JSON error pages | 429 and 503 responses match Janus API format. |
| ⚠️ Two rate limiting layers | Nginx static (30 r/s per IP) must be looser than Drools dynamic (10 r/s free tier). Confirmed correct. |
| ⚠️ TLS at Nginx, HTTP internally | Acceptable on localhost/Docker network. |
| ⚠️ Additional operational component | Nginx added to docker-compose with health checks. |
